# Durable Hermes Runs foundation — not ready for merge

`lib/agent_runs/run_client.dart` is a separately injectable REST adapter. Default Hermes sends discover capability metadata and require submission, status, structured idempotency and exact canonical endpoint descriptors. Injected coreFactory fixtures preserve their legacy behavior unless a RunClient factory is supplied. Plain providers are unchanged. Only validated HTTPS/loopback origins, optional `/p/profile` roots and canonical paths are used; redirects are refused.

The bounded secure journal (`run.v1.<local chat id>`) retains exact request JSON bytes, cryptographic Idempotency-Key, app-owned session identity, credential-scope digest and snapshots. No bearer credential enters the journal or ordinary preferences. Admission retries are explicit, use the same key and bytes and fail closed after 24 hours. Accepted admission_queued 503 is distinct from refusal. No automatic prompt replay or fresh-key fallback is implemented. Foreign native sessions remain outside this adapter.

New Hermes connections receive a fresh nonsecret authorityEpoch, persisted through the connection metadata whitelist and mirrored in controller memory. Rename preserves it; credential/endpoint/provider revisions invalidate it. Deletion and recreation with identical ID, endpoint and key cannot reconnect the old operation. Existing connections without an epoch remain compatible with pre-epoch operations; a fresh addition never inherits the supplied epoch. The existing compensating connection-write rollback mechanism is unchanged.

Terminal GET results survive journal-write failures in memory and reconcile the actual answer into the original chat. Save-only retry writes history and terminal journal state without inference. Operation-specific message IDs deduplicate history. Alerts claim a durable marker before invoking the optional notification callback: this is at-most-once, not exactly-once delivery (a crash after claim can omit an alert). Pending input comes from the actual journal after waiting/restart, not a synthesized completion.

Controller predicates scope discovery/submission/status callbacks to the captured connection-map identity, session object, operation object, pause and disposal state. Status checks apply this predicate after GET before mutating the operation or writing the journal. Unknown acknowledgement refreshes the exact admission_id/execution_generation and refreshes again on 409 without resending resolution. Typed snapshot access avoids casts on malformed status/identity/list fields. Journal loads bound size and validate required identity/payload fields, failing controller loading closed without overwriting unreadable data.

## Queue integration

Native HTTP 202 is admission only. The outbox uses a separate admitted result and holds followers without scheduling a microtask drain while the selected run is pending. Authoritative successful completion releases eligible same-source followers only after reconciliation, durable history and durable terminal journal commit. Background/conversation-switch pauses survive completion and still require Resume. History/journal failure visibly holds followers until save-only recovery followed by explicit Resume. Unknown, failed, cancelled and interrupted outcomes pause followers; unknown acknowledgement retains the exact original receipt and human side-effect warning. New drafts remain queueable/cancellable while native work runs. Legacy direct-model save recovery remains independent of native lifecycle suspension.

Controlled tests cover localhost POST202/GET-running with two followers (one POST), completion-driven continuation in the same app-owned session without replayed history, history/terminal-journal failure with save-only retry and explicit Resume, all four unsafe outcome states, preparation revocation on background/switch/map replacement, and explicit pause survival through native completion. These are local HTTP/Dart/widget checks, not live-backend or device evidence.

## Verification and explicit remaining gaps

Hardening added independently observed RED→GREEN regressions for terminal GET journal failure/save-only retry, identical-authority delete/recreate, disposal during discovery/status, durable pending input on restart, malformed/oversized journal loading, malformed snapshot typed getters, crash-window alert deduplication, and unknown-resolution exact wire identity/409 refresh. Initial foundation tests include localhost POST/GET and Reconnect widget rendering. No live backend, platform secure-storage crash, native build or device test was performed.

The follow-up hardening verifies secure-read/discovery/status and reconciliation-storage revocation matrices, exact-key/body restart after post-admission journal failure, scoped snapshot envelopes, nested schema rejection and dirty-terminal admission blocking. Ledger read-modify-write is serialized within this process for instances sharing the same SecretStore object. Durable identity and terminal snapshots/markers cannot be rolled back by stale copies; a later operation requires the exact durably committed terminal predecessor. This is not cross-process compare-and-swap or a globally exactly-once guarantee. Already-started storage writes cannot be cancelled, but stale completions cannot trigger subsequent writes, notifications or in-memory commit.

`scopedRunSnapshots` supplies local-chat and connection IDs, an opaque connection revision, operation key, immutable original-authority metadata, snapshot and revocable `isCurrent()` predicate. New approval/activity consumers must use it rather than treating a bare run ID as cross-server identity.

**Release gate:** the queue integration above is implemented and covered by controlled tests; final independent review and CI remain required before merging. Approval UI and SSE activity remain separate feature PRs. Native secure-storage/crash behavior and deployed-backend/device acceptance remain separate verification boundaries.

Verification totals are recorded in the handoff rather than hardcoded here, because the final full suite must be rerun after the last change. No dependencies, assets, changelog, production credentials, commits, pushes or releases are part of this work.
